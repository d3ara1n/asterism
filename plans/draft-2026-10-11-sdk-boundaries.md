# 工作台基础上的插件 SDK 提案

> 状态：架构方向已收敛，尚未实施。配套声明只验证接口关系，不冻结存储编码或所有字段。任务以 [插件计划](todo-2026-10-12-plugin-system.md) 为准，已确认原则见 [插件架构](../docs/architecture.md#插件)。

软件以工作台、会话、时间轴事件与资源为中心。SDK 定义宿主与插件共用的类型和接口：宿主实现基础能力供插件调用，插件提供模块与功能供宿主消费。内置 Agent 是其中一个完整消费者，其他插件可以只管理事件、状态或资源，不必认识 Agent。

## 1. 基础接口围绕会话、事件与资源

基础接口提供读取事实、提交自己的事件与状态、展示资源所需的能力。对话从时间轴记录构造，不成为所有插件的基础数据结构。

| 接口 | 责任 |
| --- | --- |
| `PluginContext` | 插件身份、配置、凭据、日志、私有目录／数据库、托管任务，取得会话与对象 context |
| `SessionHandle` | 读取固定的会话快照，追加本插件的会话事件，受控更新会话标题 |
| `ObjectContext` | 绑定目标对象，宿主每次校验归属与有效性；读取与提交状态和事件，发布对象流，不包含模型执行或对话操作 |
| `RecordContract<T>` | 声明记录的稳定身份、版本和 schema；按契约读取、解码和写入事件 |
| `ResourceContract<S>` | 声明资源数据；通过它读取资源、提供后台实现与关联视图 |

`SessionHandle.commit` 与 `ObjectContext.commit` 使用相同的同步提交规则。前者只能追加本插件声明的会话事件，不能创建对象或修改对象状态；后者绑定目标对象，可以在同一事务提交其状态与事件。宿主填来源、身份和位置，检查契约、归属、当前对象与路径，成功后通知视图。

context 与资源引用用于绑定调用和定位，不构成授权凭据。宿主继续检查真实对象和资源链接；结构类型与同进程信任不证明授权。

通用事件与资源接口不依赖内置领域类型，但消费者要解释载荷仍须显式引入对应领域契约，纯事件插件也一样。快照固定在一次读取的位置，私有状态的当前值不自动成为可恢复历史。

同一时间轴允许不同插件的记录共存。宿主先读取包含身份、顺序、契约 ID／版本、关联对象和 JSON 载荷的通用信封，不要求启用所有来源插件或认识所有载荷。插件只有在持有相应契约时才解码：

| 解码结果 | 含义与处理 |
| --- | --- |
| 不匹配（null） | 该契约不负责这条记录；保留记录，读取者可以跳过 |
| known | 身份匹配、版本支持且 schema 通过，取得具型数据 |
| unknown | 身份匹配，但版本或数据不支持；保留原始信封和载荷，使用通用显示或跳过领域处理 |

不认识载荷不是会话错误，不影响基础读取、次序与路径导航。模型记录契约属于可选模型分支的共享知识，持有它就能解码模型记录，无须认识内置 Agent。插件禁用后，其他消费者仍可凭纯契约读取历史；没有契约时不会自动加载实现或猜测字段。

core 领域共识包是确定延后实施的任务。独立命名插件读取首条用户输入时，需要 core Agent 的用户输入契约；通用信封不能推断“第一句话”的含义。资源创建、链接以及其他插件事件也须按各自领域契约解释。相关插件只引入纯契约，不必加载来源实现或共享其实例。

TypeScript 的类型在运行时擦除，不能替代 schema 校验。安全的读取来自通用信封与显式解码；静态类型语言也可以通过 JSON 载荷和未知分支实现同样的契约。

## 2. 贡献采用具体接口，减少声明层次

保留插件、模块、资源、工具与已有生命周期贡献。具名成员本身就是 extension seam，不再为每个成员建立独立的声明对象与实现对象。

| 贡献 | 收敛后的形状 |
| --- | --- |
| 插件／模块 | `definePlugin`、`defineModule`；模块返回资源、工具、记录、观察与准备贡献 |
| 资源后台 | 一个 `implementResource`，包含投影、inspect、context 与可选 creation／actions |
| 创建 | 内联 `creation: { schema, prepare?, create }`；准备在事务外，创建写入加入宿主事务 |
| 本资源动作 | 内联 `actions: { schema, prepare?, execute }`；一个输入 schema，可包含领域联合字段 |
| 资源工具 | 一个 `implementTool`；保留具型参数、结果、副作用与执行策略，宿主消费同一 SDK 接口 |
| 提交后观察 | 直接实现 `SessionObserver.committed`；不需要仅透传的 observer helper |
| 外部命令准备 | 保留已有 `CommandPreparer`，持有资源契约和输入 schema；不注册独立 Action 身份 |
| 模块关闭 | 具名 `closing`，用于收束模块自己的设施 |

创建与动作的输入 schema 是普通纯契约值，后台与 renderer 可以共同引用。没有必要为这种共享另造 CreationInput、Action 或服务目录。

本资源 prepare 与外部 preparer 均进入宿主的准备流程：外部 preparer 按插件装配顺序执行，再进入资源自身的 prepare，拒绝即停止。接受、替换、拒绝都是明确的结果类型；替换值按目标资源自己的 schema 校验后才交后续处理，不信任拦截者持有的副本。字符串可以是领域数据或持久身份，不能作为 `on("start")` 这样的泛用扩展入口。

观察只读取本次提交的固定快照，长工作交托管任务。提交后的派发按真实次序进行，处理器产生的新提交随后处理。同步回调与 writer 生命周期由宿主检查，不围绕这一约束建立额外的泛型框架。

## 3. 模型能力是一条按需使用的分支

软件保留模型与代理配置、注册等能力，用于内置功能；插件可基于模型分支实现自己的代理或资源。本轮不新增插件注册 provider 或模型实现的扩展面。普通事件或资源插件无需接触模型协议、执行策略或对话视图。

模型分支集中在 `plugin.models`：

- `roles / list` 提供已有模型与角色目录。
- `stream({ target, system, messages, signal })` 发起无状态请求，插件自行消费协议事件。
- `run(resourceRef, policy, signal)` 提供可选的模型与资源工具执行，结果仍是时间轴中的普通记录。

不公开可跨请求复用的 `PreparedModel`，也不另设 `ModelCatalog`。每次模型请求重新解析目标，来源信息随模型结果提供；`utility` 未配置模型时仍不可用。

`run` 保留为宿主的一个深模块。路径与配置取用、链接授权、工具批次、模型记录、终态、临时进度、取消和关闭在其内部收束，不拆成请求环境、批次、响应记录与活动四项公共服务。SDK 不要求插件自行按时序拼装这些步骤。

插件提供的 `RoundPolicy` 只有两个具名成员：

| 成员 | 责任 |
| --- | --- |
| `request(snapshot)` | 每次请求构造模型目标、提示、消息及工具筛选和已有轮次限制；由插件自己的事件与配置形成 |
| `next(result)` | 在正常响应与工具批次完整收束后决定是否继续；不改写宿主结果 |

模型配置、消息路径和授权在每个请求边界取用，固定到该响应与工具批次；不是整个 run 共用一份模型配置。请求次数由宿主累计，限制按当次 request 的值检查，策略不能重置计数。取消、失败、未知影响与硬停止直接由宿主终止，不进入 next。

资源引用只是地址。宿主只允许本插件为其拥有的有效对象发起 run，同一对象并发执行沿用当前的拒绝规则，关闭时统一取消。工具筛选只收窄真实链接匹配出的工具，不产生授权。

需要模型工具执行的插件可使用 run；仅消费模型的插件可自行使用 stream。两者都不需要引用内置 Agent，也不增加对话注入、对话 UI 钩子或策略成员目录。

## 4. 时间轴承载模型输出，插件自行解释领域

公共模型记录是基础事件机制的一种消费者格式。宿主保证其提交与执行归属，插件按 SDK 契约读取；用户输入、命名和代理配置等领域事件由相应插件定义。普通插件只需理解公开记录信封和自己持有的契约。

已核对现有 `projection.ts`，需要保留的信息可在同一条时间轴中表达：

| 当前投影使用的信息 | 归属 |
| --- | --- |
| 记录身份、路径次序、关联对象 | 公开记录信封与会话快照 |
| responseId、ordinal、requestParentId、complete | 公共模型记录的响应关联与完整性信息 |
| text、arguments、continuation、callId、name、outcome、scope、adapter | 公共模型协议记录 |
| 首条及后续用户输入 | 提供该功能的插件自己的领域记录 |
| 既有 event.model 与接收对象可见性 | adapter 保留到相应事件的公开数据；新领域语义由插件自己的记录表达 |

这张表是迁移核对项，不新增第三条上下文通道，也不把 model 或对话可见性加入通用 SessionRecord。旧物理节点、终态与保存的投影由 adapter 映射；具体格式与版本在对应实现批次核定。

## 5. 内置插件迁移，不扩建插件平台

全部内置功能最终只通过 SDK 消费宿主能力。core 自己实现领域资源、配置规则与视图；其他插件可以实现自己的代理和资源，无须消费 core 的领域库或实例。

迁移沿已有路径进行：

- **配置与注册：** 保留现有模型、角色与代理配置机制和页面；去掉宿主对内置 Agent schema、默认值与业务规则的依赖。存储位置与字段如何承接在实施时明确，不预先将 agents 列表删除或迁到新目录。
- **首页：** 复用创建与初始动作的内部组合。首条输入经 prepare，与会话、资源、提交幂等记录在同一事务提交，成功后启动执行；避免再次普通 submit 导致重复输入。不增加原子初始化服务、afterCreated 钩子或首页注册系统。
- **链接：** 资源定义可以用静态 `acceptsLinks` 表达接收能力，宿主检查真实对象与授权。现有内置资源仍只有 Agent 开启，不在本轮扩大工作台链接交互或引入接收策略函数。
- **视图：** renderer SDK 的基础接口承接事件读取、资源动作、创建与对象流订阅；run 的通用进度属于可选模型分支。core 视图消费相应接口，不增加任意导航、设置页或 UI feature registry。

宿主内部可以继续拆分代码与测试。只有插件实际需要改变或实现的行为进入 SDK；内部为了维护或测试而拆分的模块，不自动成为公开服务。

## 6. 实施顺序与验证

架构方向统一，按可验收的批次迁移，当前不继续扩充接口清单：

1. **事件与资源主干：** 落实声明、会话／对象读取与提交、资源／工具贡献、观察与 prepare；用不认识模型或 Agent 的插件验证。
2. **可选模型分支：** 保留一步 stream，将当前 Agent 专用 run 去领域化，集中维护执行不变量；补齐已有记录和进度的 adapter 映射。
3. **内置消费者迁移：** 先迁普通资源与命名，再迁 Agent 的策略、配置、首页与视图。清除内部类型与裸节点写入依赖；保留软件现有能力与交互。
4. **管理与验收：** 接通配置表单、流消息校验，验证独立示例与发布包。

共享实例、跨插件通信、npm 安装升级与卸载清理继续留在未来。新的记录编码和配置布局是相应批次的数据选择，不借本轮收敛提前确定。
