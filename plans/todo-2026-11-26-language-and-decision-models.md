# Separate language and decision model services

Filed: 2026-11-26. Status: Stage 1 implemented and reviewed; Stage 2 is deferred pending an explicit decision to proceed. See the [foundation review](archived/review-2026-11-26-model-category-foundation.md) for the Stage 1 disposition and the remaining integration boundaries.

## Product boundaries

- Language models and decision models are peers: each has user-configured connections and models, a catalog, a plugin-facing execution service, and host usage accounting. Peer services need not have the same execution methods.
- The host operates user-configured connections and owns credentials, model resolution, transport, cancellation, and usage attribution. Plugins own the evidence and questions they submit, when to call a model, how to interpret an answer, and what to record or do with it. An Agent can use decisions through its paradigm; configuring a model does not change Agent behavior or automatically send conversation history.
- A model reference stays `provider/model`, with the current first-slash parsing. The consuming API or selector supplies the category. Both catalogs may contain `openai/gpt-6-luna`; within either catalog the reference must be unique. A missing or disabled target in the selected catalog never resolves through the other. Cross-category indexes, configuration commands, and ledger queries carry category separately. Existing language-only references remain language references, including where older records supply the category through their owner.
- Asterism owns the request, result, capability, and usage contracts. Provider protocol and SDK library are separate implementation choices. The two planned decision protocols are **TypeSafe System One** and **OpenAI Decisions**, using their stable official JS/TS SDKs. Do not add Gemini, DMP as a separate runtime protocol, or a Vercel AI SDK decision adapter. This does not replace the existing language-model transport. A later SDK replacement, including Vercel if its decision interface becomes stable and supports both protocols, must not change a saved protocol or a plugin contract.

## Stage 1 — Language model foundation (complete)

Language configuration, execution, protocol registry, catalog, and provider account usage are category-scoped. Configuration and ledger migrations preserve existing references and classify historical model rows as language work. Stage 1 ships no decision adapter or service. See the foundation review for the scope of the SDK cutover and validation.

## Stage 2 — Add decision models as a peer service

Before starting, verify the then-current official SDK releases and wire docs for both protocols. Check custom base URLs, auth and header handling, retry defaults, abort behavior, raw response access, and whether usage and partial results survive SDK decoding. Confirm dependency choices separately. An SDK incompatibility stays at the adapter boundary; do not silently choose another transport or publish vendor types.

### Internal API and configured model parameters

Use a `decisionModels` service with its own catalog and validation, and an evaluation operation. The internal request contains an explicit target, evidence, and uniquely identified typed questions. The result matches answers to question IDs and exposes a request-level outcome and per-question results. The adapter translates a predicate into Jev `noul` or OpenAI `predicate`, and handles map versus array wire encoding. Choice returns a supplied option; ordinal score is not confidence or the most likely level; predicate probability is not confidence that the decision is right. Keep provider-defined confidence separate and do not assign a cross-provider meaning to it.

| Configuration concern | Meaning |
| --- | --- |
| Question types | Predicate, single choice, and ordinal score form the common vocabulary. Assess additional types such as Jev `box` against a real consumer; they are not assumed portable. |
| Evidence and question modalities | State which inputs can be sent as shared evidence and, where needed, which can appear inside a question. Supporting an image as shared evidence does not imply support for a question-local image; accepting conversation data as evidence does not give the decision model a tool-calling role. |
| Result capabilities | Explicit flags for choice/score distributions and per-question refusal. A predicate's yes-probability is its answer, not the optional distribution capability. Add a separate native confidence capability only if consumers need to select for it. |
| Context and shape limits | Treat tokens per request and tokens per question as separate budgets. Also consider maximum questions per request, options per choice, levels per score, and media limits where consumers benefit. Jev documents 64k per request and 32k per question by default; OpenAI documents a separate question-count limit. |
| Adapter-specific options | OpenAI cache keys and cache options or Jev long-context opt-in belong with the applicable protocol. Do not copy thinking levels, sampling temperature, max output tokens, or tool switches into generic decision configuration. |
| Price and metering | Describe this connection's pricing and billing dimensions, not those of the same named language model. Input, cached input, and output counts are distinct from price; a nonzero count can be free. |

Saved capabilities have **no unknown state**: a boolean not checked is `false`, and a type or modality not selected is unsupported. The host must not advertise or depend on disabled features even if the backend happens to return them. Do not mask an actual refusal as an answer: if a response violates the configured contract, report it rather than inventing a value. Blank optional limits mean **no additional Asterism override or cap**; they are not sent as numbers and the service still enforces its defaults. Use configured structural limits for validation; determine whether token budgets can be enforced reliably before treating estimates as hard limits. Do not silently truncate evidence or split a request to make it fit.

### Parameter lookup and discovery

Models.dev is a **reference catalog**, not an account's discovery API. The decision feed exists at [`/catalog.json?type=decision`](https://models.dev/catalog.json?type=decision) and [`/api.json?type=decision`](https://models.dev/api.json?type=decision); the compatibility feed omits specialized models by default. Asterism already performs lookup locally after loading a catalog. A model ID/name is a useful search input, but it is not unique across providers or API methods. For a decision lookup, prefer an exact provider offering and service ID in the decision category, with protocol evidence where available. Use a canonical model match only for clearly applicable facts; do not substitute another offering's prices, limits, or endpoint. Show ambiguity rather than silently picking one.

For example, the catalog contains Jev decision records and an offering for GPT-6 Luna Decisions under a gateway-specific ID. The upstream OpenAI model source declares a `decisions` route on the same `gpt-6-luna` ID as Responses. Neither an `output: 0` limit, `structured_output: true`, nor an SDK package name establishes decision capability by itself. Import only fields whose meaning is known for the selected offering: names, input modalities, applicable limits, and reference prices where available. A single catalog context number does not fill both Jev limits. Do not infer question types, distribution coverage, or refusal support just because a model is categorized as `decision`.

Lookup is an explicit draft patch. A reliable `false` may be offered as a change; missing, ambiguous, stale, or unrepresentable metadata does not set a capability to `false` or clear a limit. Account discovery and catalog enrichment are separate: for example, [TypeSafe model discovery](https://docs.typesafe.ai/api/list-models) supplies IDs, descriptions, and release dates, not a full capability table; a generic OpenAI model listing is not proof that each ID supports Decisions. Manual configuration must work without catalog coverage. Coordinate transport/version changes with [the existing models.dev v2 plan](todo-2026-11-02-models-dev-v2.md); verify the released client can obtain the required fields before committing to that integration. Stage 1 does not change the current language parameter lookup policy.

### Runtime, history, and metering

- Match responses by question ID; distinguish low probability, per-question refusal, unsupported input, malformed response, cancellation, and transport failure. Validate answer type, option identity, finite ranges and distributions, and score semantics where the applicable contract guarantees them. Never fill missing answers with negatives or zeros.
- Capture connection settings, credentials, and authorized file access at the request boundary. Reuse the host's resource/content boundary for evidence rather than implicit conversation expansion or SDK-specific file handles. A decision result is not a tool invocation. Plugins decide whether to record the decision, request confirmation, or otherwise act on it.
- Use the **same host ledger** as language models. Attribute to the plugin, purpose, session, category, and connection; retain requested model/alias and actual model ID when supplied. Observe request latency and outcomes for both categories; keep generation-only metrics on language calls, and distinguish question counts and refusals from request counts on decision calls. Partial results can still incur full usage. Count provider requests separately from logical evaluations if explicit fan-out is introduced. Exclude questions, evidence, and answers from the usage ledger.
- Trust documented per-response usage fields, not the presence of an account endpoint. Jev returns input/output token counts while charging only for input; OpenAI's cache reads and writes are included in total input and are not added to it. Keep unreported measurements separate from zero. Distinguish catalog-based estimates from provider-reported charges, and both from separately authorized organization-level reporting. Do not require admin credentials or fabricate zero cost on failure, cancellation, or missing usage.
- No silent fallback to language generation, no automatic cross-provider routing, and no hidden retries. Check SDK retry defaults; enable retries only where a concrete failure and repeat/billing semantics justify them. Report rate limits or uncertain delivery rather than casually duplicating a billed evaluation.

### Decisions to settle when Stage 2 resumes

- Choose a real plugin consumer and the smallest evidence/answer contract that serves it while testing both protocols. Decide local representation of choice IDs and ordered levels, the extent of typed provider options, and whether callers need explicit capability requirements. Do not synthesize options or probabilities incompatible with the configured model.
- Decide if connection credentials should be independently selected or reusable under one account in the settings UI, and how a genuinely cross-category picker or link supplies context. Keep raw `provider/model` unchanged.
- Decide probe semantics for a model with no reliable discovery: distinguish local validation from an explicit live test, which may transmit data and incur charges. Do not make catalog lookup or changing an editor field perform inference.
- Decide how plugins pin model aliases and calibrate thresholds when a provider or version changes; this belongs to the consumer, not a global host threshold. Permit manual review of judgments without requiring the host to keep prompts and answers.

**Completion:** The same `openai/gpt-6-luna` reference resolves independently in both catalogs and receives the appropriate capabilities and pricing; a miss in either does not cross over. The two decision adapters return the same internal shapes where semantics agree and preserve documented differences. Lookup leaves unsupplied fields untouched; an explicitly disabled capability is not advertised. Tests cover attribution and accounting for a charged partial refusal, and missing usage is not reported as free. A real plugin can use both protocols without importing either provider SDK.
