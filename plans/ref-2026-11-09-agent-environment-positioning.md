# Agent Environment: category positioning for the future website

Filed: 2026-11-09
Status: Approved category direction; website work deferred.

## Purpose

Preserve the category decision and its meaning for future website design and copywriting. This record does not initiate website implementation or change the product name.

## Approved decision

- The category name and primary website headline are **Agent Environment**.
- The product name remains **Asterism**. Agent Environment names the broader software category, not a replacement brand.
- Use the spelling `Environment` consistently.
- The marketing ambition is to establish and articulate the category's definition. This is a positioning goal, not evidence that Asterism invented the term or already owns an industry category.

## Category definition

An **Agent Environment** is a software environment in which users work with Agents, resources, and tools, compose different models of interaction and coordination, and define their own workflows.

An Agent is a participant in this environment rather than the identity of the whole application. The environment can accommodate ordinary one-to-one assistance, Router–Worker coordination, and other arrangements without making one coordinator or organizational model mandatory.

The user is part of the working environment, not merely an external source of requests. Users supply material, arrange participants and capabilities, inspect work, and decide which responsibilities to delegate.

## Asterism's expression of the category

Asterism is a local-first, composable Agent Environment. Resources, links, tools, history, and workbench views provide the common foundation across Agent paradigms.

The main paradigm is ordinary one-to-one user–Agent assistance. The built-in plugin also supplies capabilities that can realize other organizational models: a user can assign Router and Worker roles and connect them through direct Agent communication or Mesh. This does not require a new plugin or execution loop.

Paradigms and plugins are not one-to-one. Plugins provide capabilities; one plugin can support multiple organizational models, and several plugins can contribute to one arrangement. Additional plugins extend the available capabilities rather than defining a mandatory boundary around every paradigm.

Workflows remain user-defined through assistant roles, skills, task instructions, and workbench resource and link arrangements. The harness describes primitives and operation contracts rather than supplying prescribed workflows. For example, a supervisor workflow can assign an Agent the communication and follow-through that the user would otherwise perform with another Agent.

## Website expression

The primary headline is:

> Agent Environment

Use Asterism separately as the product identity. Supporting copy should explain what the environment lets users do rather than assuming the category name is self-explanatory.

Useful supporting themes are:

- Work with Agents, resources, and tools in one environment.
- Compose interaction and coordination models instead of adopting one fixed Agent organization.
- Define the workflow through roles, skills, and the workbench arrangement.
- Extend capabilities through plugins while retaining a common working environment.

`Local-first` and `composable` describe Asterism's implementation and differentiation. They need not become mandatory qualifiers in the category name or the primary headline. Final supporting copy and visual treatment remain future website decisions.

## Distinctions to preserve

| Term | Distinction |
| --- | --- |
| Agent | A participant that receives inputs and performs work; not the whole environment |
| Agent Framework | Suggests a developer library for constructing Agent systems; does not by itself communicate the user-facing working environment |
| Meta-Agent | Suggests a higher-level Agent controlling other Agents; Asterism does not require this hierarchy |
| Agent OS | Suggests operating-system-like guarantees beyond the chosen category definition |
| Agent paradigm | A general interaction and organizational model supported by available capabilities |
| Workflow | The user's concrete responsibilities, methods, handoffs, and completion criteria |

Resource-centered design is the shared foundation, not the distinguishing name of the main paradigm. Multi-paradigm composition can use existing resources; it is not synonymous with installing multiple plugins.

## Future application and evidence

When website work begins, use this decision as positioning input. Explain the category through concrete product behavior, including ordinary assistance and a Router–Worker arrangement using built-in capabilities. Present any supervisor example as a user-defined workflow, not an imposed product process.

Keep demonstrations and claims aligned with implemented capabilities. Router–Worker organization does not by itself establish every property of a named Super-agent design, such as automatic crash recovery. Independently implemented systems require explicit interaction contracts to interoperate; sharing the host alone does not prove compatibility.

No naming-availability, trademark, or category-originality investigation was performed for this decision. Claims of being first, exclusive, or an established industry standard would require separate evidence.

This record captures the positioning decision only. Website structure, final supporting copy, visual design, and implementation are deferred.
