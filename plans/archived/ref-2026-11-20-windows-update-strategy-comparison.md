# Windows update strategy comparison

Investigated on 2026-11-20 after the user's successful Windows preview acceptance. This is a source comparison and an artifact inventory, not a speed or free-space benchmark.

- [OpenChamber 2.7.3](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/electron/package.json) uses electron-builder's one-click NSIS configuration. Its [installer include](https://github.com/openchamber/openchamber/blob/v2.7.3/packages/electron/resources/installer.nsh) changes DPI awareness, not the install or replacement logic. It is an example of using the stock installer rather than building a dedicated updater.
- [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.5/apps/desktop/packaging/README.md#runtime-file-selection) extracts the replacement beside the destination, promotes it using same-volume directory renames, and removes the old backup once the install succeeds. The old tree remains available while extraction runs. Promotion failure attempts to restore it. This saves the extra write of the expanded new tree, not the need to hold the old and new trees at the same time.
- [VS Code's Windows user background updater](https://github.com/microsoft/vscode/issues/264372) prepares versioned resources and switches on restart. [Squirrel.Windows](https://github.com/Squirrel/Squirrel.Windows/blob/develop/src/Squirrel/UpdateManager.ApplyReleases.cs) extracts into an application version directory and separately cleans older versions. [Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/installer/setup/install_worker.cc) moves versioned files into place and can stage a replacement launcher when the existing executable is in use. Versioned staging moves work before activation and may retain old files, rather than necessarily using less disk. These are examples of supported paths, not claims about every distribution variant.
- [Windows Installer rollback](https://learn.microsoft.com/en-us/windows/win32/msi/rollback-installation) retains backups of deleted files and a rollback script until commit. Additional temporary storage is a common cost of rollback rather than a convention unique to NSIS.

The downloaded `v1.0.1-prerelease.1` x64 EXE is 135,577,940 bytes (129 MiB), its embedded 7z is 134,972,959 bytes, and its expanded payload is 565,149,615 bytes (539 MiB across 466 files). During the stock 7z copy step, two full expanded images plus the temporary compressed archive are about 1.18 GiB if they reside on one volume, excluding updater cache, already present files, and allocator overhead. This is a payload accounting model, not an exact free-space requirement. Putting the application on another drive splits the expanded writes between temp and the destination; it does not remove either write. Same-volume staging would leave one new expanded tree on the installation volume, but it would coexist with the old tree temporarily.

ZIP versus 7z is independent of replacement and recovery. With stock `useZip`, the old registered uninstaller still runs first, so obsolete files do not ordinarily linger, but later extraction failure still cannot restore the previous program. Leaving the uninstaller out while overlaying new files would risk stale files. The current 7z approach can recover from some failures while the old uninstaller is moving its files; it is not an end-to-end rollback if new file installation fails after old uninstall completes.

Recommendation: leave the accepted NSIS path unchanged at the current payload size absent a concrete problem with failed upgrades, time spent waiting, or cross-volume temp use. If replacement changes are justified, prefer same-volume staging and directory promotion for ordinary in-app updates over ZIP in-place or a new launcher and multi-version layout. No installation logic was changed for this comparison.
