# Skill usage tracking review

Filed: 2026-11-23

Scope: `77a79cf1` (declared usage subjects and the Skills view). This is a source review with local reproductions and a synthetic SQLite measurement, not a GUI acceptance or a production benchmark.

## Design recommendation

Keep the request-linked usage ledger. The host already knows the session, model request, calling tool, and declaration owner; recording facts at the implementation boundary gives better attribution than reparsing historical tool arguments or scanning conversation history later. Subject rows can join existing request filters without storing message bodies. A separate skill database, event bus, or host-wide access audit does not improve this feature.

Record observations separately: the user referenced a skill, the model attempted or succeeded in reading it, and the catalog occupied request context. None proves that the model applied the instructions. A successful read is a useful default measure of usage; show reference-only activity and failed attempts separately. If the goal becomes judging whether a skill description triggers discovery, track distinct first successful reads against requests where that skill was visible and readable, scoped to the relevant Agent and turn. Even that measures observed selection, not the causal effect of the description. Do not expand the public SDK or record per-skill exposure until that statistic is needed.

Request metadata should be assembled with the prompt and projected input rather than via parallel history inference and side-channel callbacks. If generic declarations remain public, keep an explicit semantic owner for reserved kinds and distinguish reporting errors from execution failures.

## Findings

1. **P1 — Telemetry can reject a valid operation.** `packages/sdk/src/usage-subjects.ts:3` limits every string to 512 characters, while the skill read path contract has no equivalent limit. `packages/builtin/src/skills/runtime.ts:37` records the raw path before reading it, and host validation throws synchronously. A temporary on-disk skill with a valid 560-character relative path read successfully without the declaration callback and failed with the host declaration callback. A 513-character unresolved `skill:` name also produces an invalid declaration; `src/plugins/sdk/execution.ts:97–100` turns the deferred validation error into a failed prompt preparation. Keep execution contracts independent of telemetry validation. Preserve valid identifiers exactly; use an explicit omitted or bounded representation for optional details when needed. Make declaration errors observable without aborting normal work. Cover a valid long path and an overlong unresolved reference at the owning boundary.
2. **P1 — The main usage metric conflates different events.** `src/telemetry/queries.ts:383–394` includes references, failed reads, and successful reads in the same request and session totals. `src/renderer/features/dashboard/views/SkillsView.tsx:35–40,71–75` treats every resulting name as used; a never-read skill leaves the unused list after a mention or failed file read. The model-chosen calculation also counts failed reads and uses any prior reference with the same name in a session, irrespective of Agent, turn, or source. A reference to one Agent in an earlier turn therefore classifies another Agent's successful read as prompted. Keep the existing exact observation labels until the system can attribute a read to prompt context; at minimum do not present this proxy as choice or description effectiveness.
3. **P2 — “First delivered” is inferred from a different stream than the actual request.** `packages/builtin/src/agent/controller.ts:212–218` scans input records and advances an in-memory mark before model preparation; `packages/builtin/src/agent/work-projection.ts:36–45` separately filters and transforms what the request receives. A transform that removes a reference still yields a declaration. On restart without a mark, `packages/builtin/src/agent/input-usage.ts:10` uses the latest output's sequence rather than its request parent, which does not establish which messages a request received or whether an attempt reached the provider. Derive retained reference metadata from the same work projection (it already carries origin information before flattening). If one count per delivered input is required, define what counts as delivery and deduplicate using input identity, not an output watermark. Add coverage for a removed reference and a request that fails before dispatch.
4. **P2 — Historical aggregation is already slow at a plausible ledger size.** `src/telemetry/queries.ts:389–394` runs a correlated anti-join per read and SQLite can walk the whole `(kind, subject_id)` range for a popular skill. On a synthetic in-memory database with 4,000 sessions, one read of the same skill per session, and no references, this SQL fragment took about 631 ms with the schema's indexes. A partial `(model_event_id, kind, subject_id) WHERE relation = 'referenced'` index reduced the same fragment to about 2 ms on the same fixture. If keeping this query, check the plan for the chosen semantics and index for it. Avoid making a single-skill detail or settings panel fetch all-time aggregates and file parts for every skill.
5. **P2 — Aggregate catalog share divides unlike populations.** `src/renderer/features/dashboard/views/SkillsView.tsx:28–45` replaces the page's subject filter to get input tokens but keeps it for the catalog character numerator. With a skill filter applied, the numerator can represent only requests with that skill while the denominator represents every catalog-bearing request. Independently, requests with unknown input tokens still contribute catalog characters. Compute both sides on the same filtered, token-reporting requests; show the average character size on its own if the token share cannot be measured.
6. **P2 — Reserved semantics are not actually scoped to the declaration owner.** `src/telemetry/subjects.ts:6–10` stamps `declaredBy`, but `src/telemetry/queries.ts:381–394` aggregates by kind and identity without using that owner; `src/plugins/sdk-runtime.test.ts:531–539` explicitly exercises another plugin declaring the same skill kind. This is a metric-ownership issue, not a plugin authorization issue. If any paradigm can intentionally contribute to the shared metric, define the common contract; otherwise namespace plugin kinds or filter the Skills view to the authoritative owner. Host-stamped attribution alone does not prevent semantic collisions.

## Follow-up disposition

The follow-up keeps the existing ledger and makes usage declarations best-effort and exact for valid identifiers. Each successful read counts once in the overview, trend, and breakdowns. Failed attempts remain in the ledger but are not shown as skill usage metrics. Agent roles and distinct turns describe the same reads, with unknown turn data kept explicit. Input-reference tracking and the model-chosen inference were removed rather than extended with more state. The catalog shows average character size instead of an estimated token share. Queries for skill details and settings select a single source and identity, and the Skills view is scoped to Builtin declarations. Historical rows remain intact and no format migration is required.
