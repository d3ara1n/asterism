# Messaging

Messaging is an application capability for communicating through configured external identities. Its meaning is independent of an Agent paradigm. The host owns connection configuration, credentials, provider registration, and shared connection lifetimes. Plugins declare providers. The SDK defines addresses, messages, events, queries, and operation contracts.

Each configured connection has its own stable identity and selects a provider type. Several connections may use the same provider. Providers declare their settings with the provider setting kinds shared by every provider family; the host renders, validates, and resolves them with the same rules and stores secrets separately from ordinary settings. Connection names identify configured accounts without assigning responsibilities or instructions.

An enabled connection shares one provider instance across sessions and consumers. Configuration changes replace it with a new generation. Only one receiver per connection runs at a time: a replacement receives after the previous generation has stopped. A model request captures the instances it can use; its operations retain that configuration, while later requests capture the updated connection. Application shutdown ends receiving work.

The host owns connection recovery. Transient creation and receive failures are retried with capped exponential backoff, or the delay the provider reports; the connection reports reconnecting with the failure being retried, and the provider's acceptance signal restores connected and resets the backoff. Terminal failures, such as rejected credentials or a conflicting receiver, leave the connection failed until its configuration changes or the user reconnects. Providers classify platform errors; the host does not interpret platform protocols. Event and status listeners are isolated from each other and from the provider, so a failing consumer cannot stop receiving.

Providers own platform protocols and the data needed to implement their operations. The host does not require a conversation index or message archive. Listing and historical reads can use remote APIs or provider-owned observations, or fail explicitly when unsupported. Query cursors belong to their provider and scope. They describe reusable positions and never acknowledge a message or advance a shared reader. Removing a connection asks its provider to release that connection's data after the receiver has ended.

Message senders carry a role relative to the connection: self, participant, or system. Roles describe the relation rather than a platform account type, so consumers can distinguish their own identity without comparing provider identifiers, and further relations can be added.

Builtin exposes two resources. Conversations lists configured connections at its root and conversations within a selected connection. Chat binds one connection and external conversation, optionally narrowed to a topic. Several resources can refer to the same external object. These references do not create independent accounts or message stores.

Resources expose communication tools through ordinary links. Exposing an Agent to a communication resource makes it a recipient of applicable events. The reverse link grants use of the resource's tools. Resource events submit facts through the public Agent input contract. Each event reaches a recipient at most once; a matching Chat, which carries the message content, is preferred over a Conversations summary. Messages from the connection's own identity are observations and are not delivered as input. Sending an external message is an explicit operation; ordinary model output stays in Asterism.

Conversations notification subscriptions begin empty. A connection subscription reports discovered conversations; a conversation subscription reports incoming messages without requiring a Chat resource. Subscriptions belong to the resource and are reconstructed from events on the current timeline path. Chat resources deliver message events to their exposed recipients. Event handling uses the current links and subscription projection of resources in the running application's current set. No automatic recipient selection or Agent creation occurs.

Views follow external activity through their projections. Each projection identifies the latest observed event for its connection or conversation while the application runs; notifications invalidate matching objects, and cards reload their queries when that identity changes. The marker identifies a change and carries no ordering or acknowledgement semantics.

Query results and their cursors are ordinary tool history. Each Agent supplies the cursor it wants to compare against. History navigation changes the Agent's available records and the resource's subscription projection, while external messages and provider observations remain real. There is no unread table, read receipt, frozen list, or per-Agent reader index.
