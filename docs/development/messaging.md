# Messaging

Messaging is an application capability for communicating through configured external identities. Its meaning is independent of an Agent paradigm. The host owns connection configuration, credentials, provider registration, and shared connection lifetimes. Plugins declare providers. The SDK defines addresses, messages, events, queries, and operation contracts.

Each configured connection has its own stable identity and selects a provider type. Several connections may use the same provider. Providers declare their settings with the provider setting kinds shared by every provider family; the host renders, validates, and resolves them with the same rules, storing secrets with the connection's other settings. Connection names identify configured accounts without assigning responsibilities or instructions.

An enabled connection shares one provider instance across sessions and consumers. Configuration changes replace it with a new generation. Only one receiver per connection runs at a time: a replacement receives after the previous generation has stopped. A model request captures the instances it can use; its operations retain that configuration, while later requests capture the updated connection. Application shutdown ends receiving work.

The host owns connection lifetimes and recovery after failed creation or receiving. Transient failures are retried with capped exponential backoff, or the delay the provider reports; the connection reports reconnecting with the failure being retried, and the provider's acceptance signal restores connected and resets the backoff. A transport may restore its protocol session within the active receive operation, reporting the interruption and recovery through the same connection states. Terminal failures, such as rejected credentials or a conflicting receiver, leave the connection failed until its configuration changes or the user reconnects. Providers classify platform errors; the host does not interpret platform protocols. Event and status listeners are isolated from each other and from the provider, so a failing consumer cannot stop receiving.

Providers own platform protocols and the data needed to implement their operations. The host does not require a conversation index or message archive. Listing and historical reads can use remote APIs or provider-owned observations, or fail explicitly when unsupported. Query cursors belong to their provider and scope. They describe reusable positions and never acknowledge a message or advance a shared reader. Removing a connection asks its provider to release that connection's data after the receiver has ended.

Builtin providers retain observations in shared storage scoped by connection identity and conversation. Message and conversation storage has no platform branches. Provider-defined recovery state is stored as opaque values alongside those observations. Providers establish aliases when the platform uses a separate reference identifier; shared lookup resolves those aliases without interpreting their contents. Removing a connection releases its observations, aliases, and recovery state together.

Message senders carry a role relative to the connection: self, participant, or system. Roles describe the relation rather than a platform account type, so consumers can distinguish their own identity without comparing provider identifiers, and further relations can be added.

Message bodies consist of ordered text and file parts. File parts describe an attachment's platform identity, MIME type, name, and known size. Every platform message retains its own identity and content. A shared group identity associates messages that the platform sends together without merging their identities, bodies, or reply targets. Providers resolve attachment bytes within the selected conversation and message using captured connection credentials. Images use the same file representation; platform upload modes and presentation remain adapter concerns.

An incoming event carries one or more messages from one conversation. Providers decide which messages belong in one delivery batch, including assembling platform media groups. Batch assembly does not change retained messages. A Chat submits the batch as one Agent input with each message's metadata and parts in order; image size and count limits apply across the entire input.

Chat resources turn platform attachment identities into resource file references addressed by message and file ID. Reading, sending, and viewing a Chat perform no content reads; consuming a reference fetches it through the provider. A new-message event fetches images within the model input limits into the input's own content scope, identifies their format from the bytes, and submits them with their references; its input record retains them. Other attachments remain references. A capture that exceeds the limits or fails keeps the reference and states the reason as text. The `see` tool fetches one image into its result on request. Chats keep no content of their own.

Builtin exposes two resources. Conversations lists configured connections at its root and conversations within a selected connection. Chat binds one connection and external conversation, optionally narrowed to a thread. Several resources can refer to the same external object. These references do not create independent accounts or message stores.

Resources expose communication tools through ordinary links. Exposing an Agent to a communication resource makes it a recipient of applicable events. The reverse link grants use of the resource's tools. Resource events submit facts through the public Agent input contract. Event processing is centralized, and each matching resource delivers independently to its exposed recipients. An Agent exposed to several matching resources receives an input from each, preserving each resource's identity and event content. Messages from the connection's own identity are observations and are not delivered as input. Sending an external message is an explicit operation; ordinary model output stays in Asterism. Sent files are file references that the provider resolves as their final consumer. Tool failures keep their messaging code and cause: reads fail, and sends fail only when the provider or platform refused them before delivery; otherwise the outcome is reported as unknown with its cause, because the message may have been delivered. Communication resources never create other resources on behalf of the user or an Agent.

Conversations notification subscriptions begin empty. A connection subscription reports discovered conversations; a conversation subscription reports incoming messages without requiring a Chat resource. Subscriptions belong to the resource and are reconstructed from events on the current timeline path. Chat resources deliver message events to their exposed recipients. Event handling uses the current links and subscription projection of resources in the running application's current set. No automatic recipient selection or Agent creation occurs.

Views follow external activity through their projections. Each projection identifies the latest observed event for its connection or conversation while the application runs; notifications invalidate matching objects, and cards reload their queries when that identity changes. The marker identifies a change and carries no ordering or acknowledgement semantics.

Query results and their cursors are ordinary tool history. Each Agent supplies the cursor it wants to compare against. History navigation changes the Agent's available records and the resource's subscription projection, while external messages and provider observations remain real. There is no unread table, read receipt, frozen list, or per-Agent reader index.
