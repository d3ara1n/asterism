# Timer and alarm resources

Each Timer resource owns one countdown and message. Each Alarm resource owns one weekly schedule and message: a local clock time on at least one weekday, always repeating. One-time delays belong to Timers. Their mutable current data preserves configuration and pending absolute deadlines across application restarts. History navigation does not restore an earlier countdown or replay a completed occurrence.

Configuration and activation are separate states. A new resource is inactive with default settings and an empty message. Model creation entries accept an empty input object. A Timer accepts configuration only while it has no pending deadline, and configuration restores its full duration. An Alarm accepts configuration only while disabled; enabling it selects the first future occurrence. Activation requires a non-empty message, because a trigger without one would deliver nothing. Resource tools and card actions share the same state transitions and validation; cards disable unavailable controls. Tools read current state at handling time, replace complete configuration, or change activation, and return the resulting state.

Each attached schedule registers its next absolute deadline with the host's shared deadline service. Configuration and activation changes replace that registration. The registration uses the resource lifetime signal; removal, session sleep, or archival cancels it. Resource attachment, not UI mounting or session selection, controls participation. Attachment reconstructs registrations from saved state on startup, wake, or restoration. A deadline cannot wake a sleeping session.

The host owns wall-clock waits, platform timeout limits, and rechecks after operating-system resume. The plugin owns saved deadlines and occurrence policy. Elapsed time during session sleep, operating-system sleep, or shutdown still counts. Each overdue resource fires once when execution resumes, independently of the others, without replaying every missed occurrence. A timer repeats by starting a full interval at the actual trigger time. An alarm repeats by selecting the next future occurrence of its local clock time on its selected weekdays. Calendar arithmetic preserves local clock time across daylight-saving changes.

Processing an occurrence first persists its next state, then submits its message independently to every directly linked Agent. A resource's message has event attribution and uses steering delivery. Scheduling does not wait for input acceptance or Agent completion, retain delivery outcomes, or retry failed deliveries. Host-managed submission tasks expose failures and end with their source resource's lifetime.
