# Timer and alarm resources

Each Timer resource owns one countdown and message. Each Alarm resource owns one calendar schedule and message. Their mutable current data preserves configuration and pending absolute deadlines across application restarts. History navigation does not restore an earlier countdown or replay a completed occurrence.

A shared backend scheduler processes attached resources across active sessions. It caches resource references and their absolute deadlines and maintains one timeout for the nearest deadline. Creation, configuration, countdown controls, enablement, and removal update that directory; changing the nearest deadline replaces the pending wait. There is no periodic scan of saved resource state and no separate runtime instance for each schedule. Resource presence controls participation; UI mounting and session selection do not. Removing a resource or archiving its session ends its participation. No pending deadline means no timeout.

When the timeout fires, the scheduler compares cached deadlines with the current wall clock and reads only the due resources. Long waits are split at the platform timeout limit without triggering resources early. Sleep and shutdown defer processing while elapsed time still counts. The host forwards system resume as a transient event; the scheduler processes overdue resources and recalculates its pending wait against the wall clock. Startup attachment reconstructs the directory from saved state. All overdue resources are processed independently. A timer repeats by starting a full interval at the actual trigger time. An alarm repeats by selecting the next future occurrence of its local clock time on its selected weekdays. Calendar arithmetic preserves local clock time across daylight-saving changes.

Processing an occurrence first persists its next state, then submits its message independently to every directly linked Agent. A resource's message has event attribution and uses steering delivery. Scheduling does not wait for input acceptance or Agent completion, retain delivery outcomes, or retry failed deliveries. Host-managed submission tasks expose failures and end with their source resource's lifetime.
