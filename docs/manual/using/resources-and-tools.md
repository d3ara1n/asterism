# Organize work with resources

Resources give material and capabilities an explicit place in the work. Linking a resource to an Agent makes that relationship visible and deliberate. A resource is more than a path mentioned in conversation, and a card is only one way of presenting it.

## Choose a useful scope

Start with the material a task actually depends on. A resource boundary should make the work understandable: which files are being changed, which conversation is being answered, or which shared notes count as current material. More linked material is not automatically better context.

Keep separate resources when their ownership or purpose differs. Share one resource when participants should work with the same current material. Two resources pointing at the same directory still reach the same files; duplicating their cards does not create isolated working copies.

Asterism's links delimit the resources supplied to an Agent and checked by resource operations. They are not an operating-system sandbox. Local programs and external integrations retain their own capabilities, so choose those environments according to the consequences of the work.

## Separate access from presentation

Card placement helps a person follow the work; links determine resource relationships. Hiding a card is a presentation choice, not a way to revoke access or stop its background activity. Removing a resource is a different decision because other work may still depend on it.

Relationships are directional. Giving one Agent access to another does not automatically give the second Agent a return route or the first Agent's resources. When planning collaboration, consider access to material, the route for assigning work, and the route for returning findings separately.

## Treat resources as current reality

Working files, notes, processes, and external services have lives beyond the conversation that mentions them. Recorded results describe what happened at a point in time; the resource may have changed since then. Returning to an earlier conversation position does not turn those current objects into their earlier versions.

This distinction matters when recovering from interruption or uncertain results. Decide what to do next from the affected resource's current state, not merely from whether the conversation contains a success message. Completed effects can survive a stopped or failed sequence, so repeating the entire sequence may repeat an effect rather than repair it.

## Distinguish a reference from a copy

A file reference names where content can be obtained. Passing it to another participant does not itself give that participant a frozen copy or put the bytes into its model context. A later retrieval can see changed content or fail because the source is no longer available.

Use live references when the purpose is to work with current material. When a decision depends on fixed evidence, preserve a stable copy and identify which version supports the conclusion. A saved conversation and a live resource answer different questions: what was observed, and what exists now.

## Agree on shared-material conventions

Shared access alone does not establish an editing order, notify every participant, or resolve disagreement. Decide who maintains the authoritative material, how proposals become accepted changes, and when others should revisit it. A shared note can be a useful coordination surface without being an automatic workflow engine.

Keep these conventions in the task, role instructions, or a selected skill. The workbench makes relationships and results inspectable; the user defines what those relationships mean for the work.
